### P0·보안·실증 인수의 안전한 절차

- **긴급 P0:** 제목에 `P0` 또는 `priority:P0` 라벨을 표기합니다. 봇은 `priority:P0`를 추가할 수 있지만 **자동 담당을 지정하지 않고** `triage:needs-review`에서 사람이 책임자를 결정합니다. 이미 수동 배정된 사람은 유지합니다.
- **보안·개인정보:** 제목의 보안/개인정보 또는 `type:security` 라벨은 자동 배정 보류입니다. 취약점 악용 방법·키·실학생 데이터·비공개 원문은 공개 이슈에 게시하지 않고, GitHub Security Advisories의 비공개 신고가 가능한 경우 사용하거나 관리자에게 비공개로 전달합니다. 봇은 공격 내용이나 비밀을 공개 댓글로 출력하지 않습니다.
- **실증 인수:** `[실증 인수]` 이슈에 관련 구현 이슈·PR/정확한 SHA, 환경, 실행자·독립 검증자, 실제 권리·계정·비용 승인, `PASS/FAIL/HOLD/NOT_RUN` 증거를 구분합니다. 봇은 담당자·실증 통과·이슈 종료를 자동 처리하지 않습니다.
- **버그·전수조사:** `[버그][코드 전수조사] P1 ...`으로 제목을 시작하면 `type:bug`, `source:code-audit`가 부착됩니다. 명확한 단일 담당 분야만 배정하며, 기존 이슈의 제목이나 담당자를 일괄 변경하지 않습니다.
- **공식 데이터 정정:** 10번째 표준 접두어를 추가하는 대신 `[데이터 요청][정정]`을 사용하며, `type:data-correction`로 구분하고 김채윤이 관리합니다.
- **추가 종류 라벨:** 문서·성능·리팩터링은 새 제목 접두어 없이 `type:docs`, `type:performance`, `type:refactor` 라벨을 사용합니다. 개별 영역 담당은 별도로 분류합니다.

### 자동 배정과 사람의 역할 경계

1. **제목 접두어는 의미가 정확해야 합니다.** 새로운 기능의 AI 작업을 서둘러 `[AI 구현]`으로 시작하지 말고 **먼저 `[추가 기능]` 이슈**를 생성합니다. 총괄의 선행 비AI 구현 후 AI 단위 작업을 독립 이슈로 발행하거나 사람/에이전트가 원 기능 담당자를 인계합니다. 봇은 **후속 인계·데이터 이슈 자동 생성·교차 리뷰어 지정은 하지 않습니다.**
2. **이슈 본문에** 실제 현상/재현 또는 사용자 목표, 영향 범위·코드 경로, 기존 연관 이슈/PR, 개인정보·출처/권리 경계, 완료/테스트 기준을 남깁니다. `[코드 전수조사]`나 `[TASK-xx]`만 제목에 붙이면 담당 분야가 명확하지 않을 수 있으므로, **앞에 표준 접두어를 추가**하거나 `[분류 검토]`로 보냅니다.
3. **라벨:** 우선순위는 제목에 `P0`/`P1`/`P2`/`P3`으로 표시하거나 `priority:P0/P1/P2/P3` 라벨을 사용합니다. 작업 강도는 사람이 `effort:S`(1점), `effort:M`(3점), `effort:L`(8점) 중 하나를 부여합니다. 미추정에는 `effort:unestimated`가 붙고 계산상 3점을 임시로 사용합니다. 봇이 실제 시간을 예측한 값이 아닙니다.
4. **사람이 수동 배정한 담당자는 유지됩니다.** 접두어와 `area:...` 라벨이 서로 다르거나 영역 라벨이 복수인 경우에는 봇이 `triage:needs-review`를 붙여 보류합니다. 역할이 확인됐을 때만 단일 `area:integration/ai/web/data`를 사용하고, `routing:hold`로 자동 배정을 잠시 막을 수 있습니다. 기존 담당자 일괄 재배정은 없습니다.
5. **작동 확인:** 새 이슈 생성 후 [GitHub Actions](https://github.com/ot4562-glitch/HUFS-One-AI/actions)에서 `Issue triage and fair assignment`가 실행됐는지 보고, 예상 라벨·담당자·로그를 확인합니다. 실패/미설치/분류 보류라면 [봇 운영 안내](ISSUE_ROUTING_BOT.md)를 따라 수동 검토합니다. 기존 이슈 재분류는 `workflow_dispatch`에서 해당 이슈 **하나씩** `dry_run=true` 미리보기 후 실행합니다.
6. **절대 금지:** #355–#359 및 `[본선 진출 이후]`·`[본선진출이후]` 접두어 이슈의 제목·본문·담당·라벨·마일스톤·상태를 수정하지 않습니다. **진행/인수는 새 댓글 작성만 허용**합니다(기존 댓글 삭제/덮어쓰기 금지). 수정 API 호출 전 이슈 번호·현재 제목을 읽고 해당하면 중단합니다. `csv/` 5개 원본/학생 개인정보/비밀·미확인 학교 자료를 이슈·PR·로그에 붙이지 않습니다. 합성 성공을 실서비스 완료로 혼동하지 않습니다.

**이슈 템플릿은 제목 접두어를 미리 채워 주지만, 에이전트가 API/CLI로 만들 때도 이 규칙이 동일합니다.** 기술적으로 분류 가능하다는 이유만으로 과도하게 자동 배정하지 않고, 모호하면 사람이 판정하도록 남깁니다. [봇 운영·산식](ISSUE_ROUTING_BOT.md) · [PR/리뷰·검증](PR_WORKFLOW.md).

## 2. 추가 기능 생명주기: 심민성 구현 우선 → AI 구현 인계

**단계 A — 최초 구현(심민성).** 신규 기능 이슈를 `assignees=['ot4562-glitch']`로 만든다. 기존 자료와 현재 구조/PR을 읽고 **할 수 있는 범위까지 Core/Contracts/API/DB/인증·권한·비AI 화면 연계/순수 비즈니스 로직·통합/자동 테스트를 직접 구현**한다. 설계만 남기고 기계적으로 조기 이관하는 방식은 기준이 아니다.

**단계 B — 데이터 필요성 점검.** 공식 문서·학칙/공고·포스터·행사·멘토·상담기관·NCS·배지·학습 프로그램·취업통계·다국어 안내·이미지 게시권·독립 Gold가 필요한 경우 **새 `[데이터 요청][김채윤]` 이슈**를 만든다. `assignees=['qamarrchae']`, 기능 번호/필요 필드/공식 출처·판본·목적별 권리·Gold·UI asset·희망 인수 시점/상태를 적는다. **기능 이슈에도 김채윤을 공동 assignee 추가**한다. 이슈 쌍을 서로 연결한다. 현재 13개 기능의 공통 대규모 요청은 [#360](https://github.com/ot4562-glitch/HUFS-One-AI/issues/360)을 사용하고, **추가 기능·새 범위에 대해서는 새로운 별도 데이터 이슈를 생성**한다. 같은 범위/원장 이중 요청 여부를 확인한다.

**단계 C — AI 코드 충돌/겹침을 발견하면 즉시 인계.** AI 범위에는 **HCX-007·CLOVA OCR·RAG·NLP·문서/의미 추출, 규칙·가중치·스코어·랭킹·Jaccard/BM25/TF-IDF·임베딩·ML·예측/개인화 추천, AI 정확도/비교 실험**이 포함된다. LLM을 호출하지 않는 **코드 기반 AI도 동일하게 AI 작업**이다. 이 부분의 실개발 주담당은 **박준영 또는 이의상 중 한 명**으로 지정한다. 주로 추천·랭킹·예측/정량 QA는 박준영, OCR/NLP/RAG/문서/다국어 처리 등은 이의상이 자연스러운 출발점이지만 **두 사람은 두 기술 영역을 모두 개발할 수 있고 작업량·기존 담당/코드 소유에 따라 자유롭게 조정**한다. 상대방은 필수 교차 리뷰/피드백에 참여한다.

**단계 D — 담당자 기록.**
- AI 기능 단계 진입 후: `assignees=[선정한 AI 주담당]` + (데이터 필요 시 `'qamarrchae'`). 심민성은 기능 코어의 **비AI 인프라/계약·보안/통합 코드 구현과 상시 리뷰**를 계속 수행할 수 있으며, 이 진행은 이슈 댓글/PR에 남긴다.
- AI 코드가 없어 끝까지 일반 기능인 경우: `assignees=['ot4562-glitch']` + (데이터 필요 시 `'qamarrchae'`). 개인별 고정 역할 이슈와 분리한다.
- 데이터 요청: `assignees=['qamarrchae']`, 신규 기능 번호와 인수 항목 연결. 웹 디자인은 이서연이 UI 서브작업/PR을 인수한다.
- AI QA는 **박준영**, 사용자 관점 가벼운 전 과정 시연·제보는 **김채윤**, 웹 디자인·기능 연결은 **이서연**, 코드와 품질의 상시 통합 검수는 **심민성**이다.

**단계 E — 완료 판단.** 이슈의 실제 PR SHA·CURRENT HEAD CI·비작성자 코드 리뷰·실데이터/권리·독립 Gold·HCX/OCR 시험·UI 실제 배치·사용자 시연/기술 QA·실운영 영수증을 **각기 다른 증거**로 기재한다. PR Open/합성 PASS는 실서비스 완료가 아니다.

## 4. 절대 유지할 안전 경계

- `csv/`의 기존 **Google Forms 1개 + 개인별 수강 CSV 4개**는 보존하고 임의 삭제·수정·재인코딩·이동·공개 웹/운영 이미지 포함을 방지한다. 비밀·실명/SID·학생 원본 자료를 새 공개 이슈/PR에 담지 않는다.
- 자료·포스터의 읽기/게시/OCR/HCX-007 전송·보존·철회 권리는 목적별로 확인한다. 합성 fixture는 독립 사람 Gold가 아니다.

- 테스트 미실시 `NOT_RUN`, 운영 미연결 `NOT_CONNECTED`, 설정 미완 `CONFIGURATION_REQUIRED`, 출시 미인수 `RELEASE_BLOCKED`를 유지한다.
