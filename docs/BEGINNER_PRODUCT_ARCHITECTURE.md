## 0. 30초 요약

**HUFS One AI는 한국외국어대학교 학생의 ‘개인 상황에 맞는 기회·공지·경험·학업 계획’을 한곳에서 정리하고, ‘왜 이런 결과가 나왔는지’ 근거를 보여 주려는 독립 학생 프로젝트**다. 학교의 공식 학사 시스템이 아니며 졸업·지원 자격·합격 가능성을 무조건 확정하지 않는다.

예를 들면 학생이 다음을 한 화면에서 확인하고 싶을 때 사용한다.

- “내 관심사와 전공에 맞는 교내외 활동은 무엇이고 **신청 마감이 언제인가**?”
- “내가 기록한 경험을 AI가 어떤 역량으로 **제안**하고, 내가 어떤 태그를 **승인**할까?”
- “이번 학기의 이수·수강중·수강계획은 무엇이며 **아직 검증되지 않은 부분**은?”
- “학칙과 개설 근거가 없다면 무엇을 확인해야 할까? 전공 변경을 가정하면 어떤 문제가 생길까?”

**목표는 AI가 모든 결론을 대신 내리는 것이 아니라, 학생이 확인할 정보·근거·다음 행동을 정리하도록 돕는 것**이다.

## 1. 서비스의 핵심 부품 7개

| 부품 | 쉬운 비유 | 실제 기술·저장소 위치 | 하는 일 |
| --- | --- | --- | --- |
| ① **웹 화면** | 학생이 쓰는 안내 창구 | React + Vite, `apps/web` | 메뉴·카드·로그인 상태·데이터 표시 |
| ② **API 서버** | 창구 뒤 직원·규칙 집행자 | Fastify, `apps/api` | 요청을 받고 인증·권한·버전 확인 |
| ③ **공통 계약** | 모든 창구가 따르는 같은 양식 | Zod, `packages/contracts` | 주고받는 데이터 형식/값 검증 |
| ④ **추천·학업 계산 코어** | 정해진 계산표 | TypeScript, `packages/core` | 추천 순위·조건·학점·가정 시뮬레이션 계산 |
| ⑤ **데이터베이스** | 사용자별 잠긴 기록 보관함 | PostgreSQL, `infra/sql` | 프로필·이력·승인·근거·동의·버전 저장 |
| ⑥ **AI·원문 처리** | 글을 읽고 **초안**을 제시하는 보조 담당 | `packages/ai` 및 `apps/api/src/modules/ai` | OCR·CLOVA/HCX 결과 후보·근거·비용 검증 |
| ⑦ **클라우드·보안·운영** | 건물·문·비상대피 계획 | `infra/ncp` / `infra/deploy` | NCP 서버·HTTPS·방화벽·백업·복구·비용 관리 |

웹 화면은 보이는 부분이고, 중요한 **“당신이 누구인지·이 자료가 당신 것인지”의 판단은 서버에서 한다**. 브라우저가 보낸 “나는 학생 A다”라는 글자만 믿지 않는다.

## 3. 학생이 보는 화면은 어떻게 만들어질까?

### 3-1. 브라우저에서 시작

`apps/web/src/main.tsx`가 React 앱을 시작한다. 페이지와 메뉴는 `App.tsx`, `apps/web/src/pages`, `apps/web/src/shell` 등에 있다.

- **오늘:** 중요한 공지·기회·마감·일정을 빠르게 확인하려는 영역.
- **기회:** 공고·비교과/대외활동 등의 조건·마감·추천 이유.
- **경험:** 학생이 직접 기록한 활동·수상/프로젝트/역할 등의 설명과 AI 태그 *후보*.
- **졸업/학업:** 이수·수강중·계획·복수/이중전공 What-if 및 근거·미검증 상태.
- **보관함/지원 현황:** 북마크·할 일·신청 과정의 **사용자 기록**. 외부 기관에 실제 지원서를 제출했다고 자동 주장하지 않는다.

메뉴가 보인다고 모두 공식 학교 기능과 연결된 것은 아니다. `HUFSAbility` 원래 메뉴 중 연결 근거가 없는 것은 **미지원**으로 표시한다. 이 프로젝트는 한국외대 공식 제품을 사칭하지 않는다.

### 3-2. 버튼 하나를 누르면?

예를 들어 학생이 “내 수강 자료 보기”를 누르면:

1. 브라우저는 `/api/private-intake/self`로 **본인 자료만** 요청한다. 학생 번호·파일 이름·다른 사람 ID를 선택해 보내지 않는다.
2. Fastify 서버가 실제 **BETA 로그인 세션** 및 학교 메일 확인·현재 권한을 검사한다.
3. 운영자가 별도로 검증한 **학생 배우(actor) ID ↔ Forms 응답 행 ↔ 이수과목 CSV 원본 해시 ↔ 현재 동의/철회** 연결을 확인한다.
4. 연결·원본·보안 조건이 맞으면 학생의 **자기 프로필·교과 기록**만 정해진 JSON 양식으로 응답한다. 응답 직전에 권한과 원본이 바뀌지 않았는지 다시 확인한다.
5. UI는 과목명·학기·학점·학수번호·이수상태를 보여 주며, 원본에 값이 없으면 **미확인**으로 표시한다.

**주의:** 이 API·화면 연결 코드는 있지만, 실제 운영자 identity registry·DB 구성/라이브 로그인·실서버 설정이 없는 환경에서 **실제 학생 정보가 자동 표시되지는 않는다**. 단순히 CSV를 DB에 추가한다고 자동 매핑되지 않는다. 현재 operator 조립·NCP 실서비스 연결은 실제 검증이 필요한 단계다.

## 4. “합성 5명”과 “실자료 4명”은 다르다

| 구분 | 합성 S01~S05 | CSV 실제 응답 4명 | REVIEWER |
| --- | --- | --- | --- |
| 정체 | **만들어 낸 가상의 시연 프로필** | 실제 양식을 제출한 개별 제공자 | 초대된 심사자 역할 |
| 왜 필요한가 | 데이터가 없어도 UI·추천·버튼 시험 | 본인 확인 후 실제 데이터 기능 검증 | 타인 개인정보 없이 데모 평가 |
| 허용되는 자료 | 가짜 공고·가짜 학생·합성 성적 | 현재 동의·소유 확인된 자신의 원본 | 제한된 합성·심사자 sandbox |
| 주의할 점 | 진짜 학생/공식 학업 데이터라고 설명하면 안 됨 | 파일명만으로 로그인 계정을 추정하면 안 됨 | 실자료 권한이 생기지 않음 |

복구된 `csv/`에는 **Google Forms CSV 1개 + 개인별 수강 CSV 4개 = 원본 5개**가 있다. 프로젝트 지시에 따라 원본을 무단 수정·삭제·이동·재인코딩하지 않으며 [데이터 관리 정책](DATA_GOVERNANCE.md)과 blob SHA 보존 검사를 따른다. 이 원본이 **공개 Git에 존재한다는 사실**은 다른 사람에게 학생별 열람·재전송 권한을 주는 것이 아니다. 실제 서비스 데이터가 읽히려면 사용자별 인증·현재 동의·목적/권리를 별도로 검증한다.

**대표적인 오해:** “학생 4명 데이터를 이미 확보했으니 학교 공고와 졸업 요건도 실제로 판정된다.” → 아니다. 수강 CSV는 개인이 제공한 내용이며, 공식 과목 코드·학칙 RulePack·개설 내역과 검증된 연결이 부족하면 `UNKNOWN` 또는 `NEEDS_REVIEW`로 둔다.

## 5. 추천의 원리 — ‘내 조건에 맞을까?’를 계산

추천은 단순히 생성형 AI가 인기 순위를 말하는 것이 아니다. 기본 로직은 **규칙과 증거를 바탕으로 한 계산**이다.

~~~text
내 관심사·희망 분야·승인된 경험·전공(있는 경우)
                     +
 공고의 주제·자격요건·마감일·출처·유효한 판본
                     ↓
     공고 자격/불확실성 검사 (확인됨 / 불명확)
                     ↓
           관련성 점수와 근거 설명
                     ↓
         학생에게 목록·이유·마감 표시
~~~

- 같은 활동도 **관심 분야**가 다르면 추천 순위가 달라질 수 있다.
- **지원 가능** 판정과 **관심에 맞음**은 별개다. 점수가 높아도 실제 지원 자격이 확인되지 않았다면 자동 확정하지 않는다.
- AI가 “활동 경험이 좋다”고 쓴 **초안**을 학생이 승인하지 않았다면, 실제 역량 인증이나 추천 입력의 확정 사실로 사용하지 않는다.
- 추천 점수는 **합격 확률/취업 성공률**이 아니다. 현재 실측하지 않은 정확도 향상을 확정 효과로 표현하지 않는다.

기술 자료: [추천 코어](../packages/core/src/opportunities/README.md) · [데이터/권한 계약](Architecture.md#contract-boundaries).

## 6. 학업 계산의 원리 — 취득·수강중·계획을 분리

예를 들어 3학점짜리 과목을 두 개 수강 완료한 학생이라면 **취득 6학점**으로 기록할 수 있다. 그러나 “전공 필수 몇 학점이 남았나?”는 더 많은 근거가 있어야 답할 수 있다.

| 구분 | 의미 | 졸업 판정에 바로 쓸 수 있나? |
| --- | --- | --- |
| `EARNED` | 이수 완료로 등록된 과목 | 공식 원장·과목/이수구분 검증 필요 |
| `IN_PROGRESS` | 현재 수강 중인 과목 | 이수 확정과 **다름** |
| `PLANNED` | 앞으로 수강하려고 기록한 과목 | 취득 학점에 더하면 **안 됨** |
| RulePack | 입학년도/캠퍼스/전공별 검토된 규칙 묶음 | 출처·예외·승인 범위까지 확인해야 함 |
| What-if | 복수전공 제외 등 “만약”을 가정한 계산 | 실제 전공 변경/졸업 신청이 아님 |

실제 학업 결과에는 과목 코드, 동등 과목/중복 인정, 재수강, 학생의 입학 연도, 학칙 개정 적용 시점이 영향을 준다. 증거가 빈칸인 항목은 값을 **억지로 채우지 않고** `UNKNOWN`으로 보여 준다. 저장소의 학업 코어는 `packages/core/src/academics`, 실제 owner 자료 로더/검증 코드는 `apps/api/src/modules/academics`에 있다.

## 7. 경험→AI→학생 승인 흐름

학생이 “경제학 연구 프로젝트에서 데이터 분석을 담당했다”고 기록했다고 하자.

1. **학생이 직접 경험을 작성**한다. 현재 계정/버전/수정 권한을 저장한다.
2. AI 사용을 선택했다면 서버는 그 경험이 **본인 소유, 현재 이용 동의, 허가된 외부 전송 범위, 원문/자료 버전, 예산**에 맞는지 확인한다.
3. 서버가 필요한 자료만 **CLOVA 모델**에 보내어 역량·설명 후보를 구조화한다. OCR은 승인된 이미지/PDF의 문자 확인에 선택적으로 사용한다.
4. 결과는 **“AI 후보 / 검토 필요(NEEDS_REVIEW)”**로 저장한다. 실경험의 사실 자체나 공식 자격이 되는 것은 아니다.
5. **학생이 직접 채택·수정/승인**한 태그만 이후 관련성 계산의 승인된 입력에 사용할 수 있다. 경험 원본·동의가 바뀌거나 삭제되면 기존 승인 유효성을 다시 검사한다.

이 흐름에는 **개발 에이전트 Codex/Claude Code가 필수가 아니다**. 학생용 제품 AI와 개발 작업을 돕는 터미널 에이전트는 서로 다른 소프트웨어다.

## 8. RAG·출처·시점은 왜 중요한가?

**RAG**는 AI에 질문만 던지지 않고 **관련 문서·근거를 찾아 함께 전달하는 방식**이다. 여기서는 특히 **출처가 어디인지, 언제 게시·수정됐는지, 그 버전을 읽을 권한이 있는지**가 중요하다.

예를 들어 공고의 지원 마감이 11월 15일에서 11월 12일로 정정됐다면, 시스템은 **오래된 요약을 새 공고인 것처럼 쓰지 않고** 원문 버전(`SourceRevision`)을 구분해야 한다. 미래에 알게 된 정정 정보를 지난 시점 추천에 무심코 섞지 않는 것도 중요한 조건이다.

OCR/이미지에서 읽어 낸 문자도 자동으로 진실이 아니다. 숫자·날짜·링크·조건은 원문과 비교해 오류를 잡거나 `NEEDS_REVIEW`로 보류한다. [원문/RAG/시점 설계](Architecture.md#trusted-rag-media-versioning)를 참고한다.

## 9. 왜 DB에 전부 넣고 모두 보여 주지 않나?

**개인정보와 신뢰 때문이다.** 한 학생의 과목·경험·프로필은 다른 학생이 볼 이유가 없다. 서버에 자료를 저장하는 것과 그 자료를 브라우저에 공개하는 것은 별개다.

1. 로그인할 때 **진짜 사용자 ID**를 서버가 확인한다.
2. 필요한 **기능별 권한**을 검사한다. `BETA` 학생은 자신의 자료, `REVIEWER`는 제한된 합성, `ADMIN`은 필요한 관리 기능만.
3. PostgreSQL **RLS(Row Level Security)**는 “이 사용자 ID에 해당하는 행만” 보이도록 DB 차원에서 한 번 더 잠근다.
4. **Zod 계약**은 응답에 불필요한 비밀값·학생 ID·알 수 없는 필드가 섞여 들어오면 거부하는 추가 검사 역할이다.
5. 변경할 때 **version/CAS**를 검증해 오래된 화면이 다른 변경을 덮어쓰지 않게 한다.
6. 공유·동의·학생의 삭제/철회가 바뀌면 이전 결과를 계속 사용하지 않고 다시 확인한다.
7. 브라우저의 요청은 **CSRF 보호·현재 세션**에 따라 처리하고, 서버 DB/API key는 웹에 넣지 않는다.

CSV 5개를 GitHub에 보관하는 보존 지시는 **그 내용을 브라우저·에이전트·로그·공개 ZIP에 넣어도 된다는 뜻이 아니다**. 학생별 권리는 현재 상태로 검증하며, 합법적인 철회/삭제 요구는 무단 보존보다 우선한다.

## 10. GPT와 Claude는 어디에 들어가나?

| 이름 | 이 프로젝트에서의 의미 | 어떻게 작동하나? |
| --- | --- | --- |
| **Codex(GPT 개발 에이전트)** | 개발자가 코드를 읽고 테스트/수정 초안을 만들 때 쓰는 도구 | `codex` CLI를 개발자 개인 PC나 격리 NCP 환경에서 실행 |
| **Claude Code** | 같은 종류의 개발용 보조 도구 | `claude` CLI를 개발자 개인 계정에서 실행 |
| **CLOVA Studio HCX** | 실제 학생 서비스용 AI 후보 생성의 **현행 구현 대상** | Fastify 서버가 승인된 입력·예산을 확인한 뒤 NCP HTTPS API 호출 |
| **CLOVA OCR** | 권한 있는 이미지/PDF에서 문자열 추출 보조 | 서버측 OCR 계약과 원문/이미지 권리, 건수/비용 검증 |

특히 **Codex 또는 Claude Code를 ‘NCP에 설치했다’는 사실과 ‘제품에 AI가 붙었다’는 사실은 다르다.** [제품/에이전트 설치 가이드](BEGINNER_NCP_PRODUCT_AND_AGENTS.md)를 참고한다.

## 11. NCP 서버가 하는 일과 하지 않는 일

NCP 서버를 **도서관 건물**이라고 생각하면 다음과 같다.

- **서버(건물):** 코드를 실행할 공간을 제공한다.
- **도메인/HTTPS(현관·안내):** 학생이 안전하게 접속하는 주소와 통로다.
- **React(안내판):** 학생이 보는 내용을 그린다.
- **Fastify(담당 직원):** 학생의 신분·요청을 확인한다.
- **PostgreSQL(잠긴 서류실):** 학생별 기록을 보호·보존한다.
- **코어(규칙표):** 학점·추천·날짜를 비교한다.
- **CLOVA(선택 보조):** 근거를 읽고 후보를 써 주지만 최종 결정을 하지 않는다.
- **백업/운영 기록(비상 대피/복구):** 고장/오류/비용 문제에 대비한다.

**서버만 개설했을 때**는 건물이 빈 상태다. 프로젝트 코드가 `git`에 있다고 해서 입주가 끝난 것이 아니다. 게다가 현재 **합성 미리보기**는 이 건물의 외부 공개 문을 닫고 **SSH 관리인만** 시험하는 단계이며, 실서비스는 HTTPS·OIDC·DB·학교메일·현재 동의/권리·인수라는 추가 단계가 필요하다.

## 12. “이 기능은 실제로 됩니까?” 판단법

서비스 설명과 구현 상태를 혼동하지 않기 위한 용어를 기억한다.

| 표시 | 의미 | 예시 |
| --- | --- | --- |
| `SYNTHETIC` | 개발용 가짜 데이터 | 5개 가상 학생과 합성 공고 |
| `OWNER_CONFIRMED_APPROVED` | 프로젝트 소유자가 해당 개발/운영 계획 승인 확인 | **코드 성공·실제 학생별 동의와 별개** |
| `CONFIGURATION_REQUIRED` | 코드는 있으나 실제 설정/계정/키/연동이 필요 | Google OIDC·NCP 서버 비밀 |
| `NOT_RUN` | 아직 현장 시험을 하지 않음 | 실제 외부 사용자 DB/로그인·유료 호출 |
| `NOT_MEASURED` | 수치를 재지 않았음 | 실 응답시간·월비용·정확도 |
| `NEEDS_REVIEW` | 원문/사용자 확인·사람 판단이 필요 | AI 후보·과목 코드·학칙 예외 |
| `UNKNOWN` | 판단할 증거가 모자람 | 검증되지 않은 공식 졸업 요건 |
| `RELEASE_BLOCKED` | 필수 운영 인수 조건이 남아 있어 출시 완료로 표시할 수 없음 | 현재 운영 통합 이슈 |

**정리:** 파일·코드·테스트가 ‘존재한다’와 ‘실제 학교 자료로 운영된다’는 다른 명제다. 팀이 정직하게 보고하기 위해 이 상태를 분리한다.

## 13. 개발자를 만났을 때 물어볼 다섯 가지

1. **학생 A의 데이터는 B에게 절대로 보이지 않는가?** → 서버 ID/SQL RLS와 부정 테스트 확인.
2. **실제 자료가 틀리면 무엇이라고 표시하나?** → UNKNOWN/NEEDS_REVIEW와 근거 확인.
3. **AI가 거짓 정보를 쓰면 어떻게 막나?** → 허가 입력, 구조 검증, 학생 승인 전 확정 금지.
4. **서버에 문제가 생기면 어떻게 복구하나?** → NCP 호스트 접근·last-good 버전, DB 백업/복원.
5. **실제 운영비와 개인정보 처리는 누가 책임지나?** → NCP 계정/청구/운영·현재 권리·폐기 담당과 증거 문서.

기술 담당은 프로젝트 [AGENTS](../AGENTS.md)와 현재 [STATUS](../STATUS.md), 실제 통합 준비는 [#276](https://github.com/ot4562-glitch/HUFS-One-AI/issues/276)에서 확인한다.

## 14. 비전공자 10분 설명·발표 구성

| 시간 | 무엇을 보여 주나 | 반드시 덧붙일 말 |
| --- | --- | --- |
| 0~1분 | 학생의 기회·공지·경험·학업 정보가 흩어진 문제 | 학교 공식 서비스가 아닌 독립 프로젝트 |
| 1~3분 | 합성 화면의 오늘·기회·마감·추천 이유 | 합성 데이터는 가상의 학생/공고 |
| 3~5분 | 경험 기록 → AI 후보 → 학생 승인 | AI 자동 인증 아님, 사람 결정 |
| 5~7분 | 학업 원장과 What-if에서 불확실성/미확인 강조 | 공식 졸업/전공 변경 승인 아님 |
| 7~9분 | React/API/DB/권리/클라우드 흐름 그림 | NCP plan·합성 CI와 실운영 성공을 구별 |
| 9~10분 | 기대 효과와 검증/남은 과제 | 미측정 효과·실비용/실사용은 미확정으로 설명 |

60초 버전:

> “HUFS One AI는 학생의 활동 기회와 학업 기록을 한 화면에 모으고, 학생의 관심과 승인된 경험을 기준으로 추천 이유를 보여 주는 독립 학생 프로젝트입니다. AI는 정보를 읽어 제안할 수 있지만 자격이나 역량을 함부로 확정하지 않습니다. 현재 합성 시연·코드·보안 검증은 존재하며, 실제 로그인·데이터 권리·NCP·학교 근거 검증이 완료돼야 실서비스로 전환됩니다.”

## 15. 내가 직접 확인하는 방법

개발 PC에서 **실제 계정·외부 서비스 호출 없이** 합성 시연하려면 [DEMO_MANUAL](OPERATIONS.md#demo-manual)을 먼저 읽는다. 예를 들면 저장소에서 Node 버전을 확인하고 다음 두 터미널을 **별도로** 실행한다.

~~~bash
# 사전 1회: 의존성 설치(개발 PC)
npm ci --ignore-scripts --no-audit --no-fund

# 터미널 1: 합성 계정 API
npm run start:api:synthetic-accounts

# 터미널 2: 합성 웹
npm run dev:web -- --mode synthetic
~~~

`http://127.0.0.1:5173`에서 데모 UI를 본다. **실 NCP 서버, 학생 자료, 유료 모델이 없어도** 개발 기능을 확인하기 위한 방식이다. 접속 실패는 포트 충돌·Node 버전·API 부팅 오류 등을 먼저 확인한다.

서버를 직접 마련하려면 [NCP 서버 설정](BEGINNER_NCP_SERVER_SETUP.md) → [제품·개발 에이전트 설치](BEGINNER_NCP_PRODUCT_AND_AGENTS.md) 순으로 진행한다. 실제로 일반 학생에게 공개하려면 별도 [운영 런타임 가이드](PRODUCTION_RUNTIME.md)와 [운영 이슈 #276](https://github.com/ot4562-glitch/HUFS-One-AI/issues/276)의 실증 조건을 완료해야 한다.
