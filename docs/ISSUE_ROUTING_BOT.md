# HUFS One AI — 이슈 자동 분류·공정 배정 봇

기존 [AGENTS](../AGENTS.md) 및 [신규 이슈 배정 플레이북](ISSUE_ASSIGNMENT_PLAYBOOK.md)의 **단계별 인계 규칙을 유지**하면서, 새 이슈에 영역·우선순위·난이도 추정 필요 라벨을 부착하고 담당자를 초기 배정합니다. 외부 AI API·유료 서버가 필요하지 않습니다.

**절대 변경 금지:** 고정 역할 이슈 **#355–#359** 또는 `[본선 진출 이후]` 제목. 봇은 라벨·담당자·댓글을 포함한 모든 쓰기를 건너뜁니다. 오래된 #321–#325를 현재 역할의 기준으로 재사용하지 않습니다.

## 공정 배정 산식

- `effort:S=1`, `effort:M=3`, `effort:L=8`점. 난이도를 정하지 않았다면 `effort:unestimated`를 추가하고 **임시로 3점**으로 계산합니다. 자동으로 L/M/S를 추측하지 않습니다.
- 담당 가능 인원의 열린 이슈에서 **각자 배정된 작업의 점수 합 / capacity**를 비교하고 가장 낮은 담당자를 선택합니다. 동률이면 열린 이슈 개수, 마지막으로 GitHub ID 순으로 결정합니다.
- PR과 고정 역할 이슈 #355–#359는 계산에서 제외합니다. 데이터 공동 담당처럼 하나의 이슈에 여러 명이 있으면 각각의 열린 업무량에 반영합니다. 역할별 단독 담당자에게는 가상 경쟁자를 만들지 않습니다.
- `capacity`는 현재 모두 1로 두었습니다. 실제 가용 시간에 합의가 생기면 [설정](../.github/issue-routing.json)에서 변경합니다. **업무량 점수는 실제 시간이나 개인의 성과 평가가 아닙니다.**
- 현재 할당량은 생성·편집 시의 스냅샷입니다. 이 봇은 기존 이슈를 임의로 재분배하지 않습니다.

## 사용법

1. 저장소 [Actions](https://github.com/ot4562-glitch/HUFS-One-AI/actions)에서 **Issue triage and fair assignment** 워크플로가 활성화되어 있는지 확인합니다. 이 PR이 기본 브랜치에 병합된 뒤부터 새 이슈의 `opened / edited / reopened / labeled / unlabeled` 이벤트에서 실행됩니다.
2. [최초 방문 에이전트용 표준 접두어 표](ISSUE_ASSIGNMENT_PLAYBOOK.md)를 보고 이슈 제목 앞에 `[추가 기능]`, `[AI 구현]`, `[AI QA]`, `[웹 구현]`, `[데이터 요청]`, `[기술 통합]`, `[분류 검토]` 중 하나를 붙입니다. [GitHub 이슈 템플릿](../.github/ISSUE_TEMPLATE/)을 선택하면 미리 채워집니다. 제목 앞에 `[코드 전수조사]`만 두거나 혼합 분야를 임의로 담당 지정하지 않습니다. 실제 상황·근거·수용기준·연관 이슈를 작성합니다.
3. 사람이 자동 분류를 보완하려면 **한 개의** `area:ai`, `area:web`, `area:data`, `area:integration` 라벨을 부착합니다. 영역 라벨이 여러 개면 `triage:needs-review`로 남깁니다. 잘못 붙은 기존 영역 라벨은 직접 제거하세요.
4. 기존 담당자가 이미 있으면 **자동 배정을 하지 않습니다**. 자동 배정을 잠시 막으려면 `routing:hold` 라벨을 만듭니다(`Issues → Labels`) 및 부착합니다. `triage:needs-review`는 분류가 해결되면 봇이 제거합니다.
5. 우선순위를 표시하려면 제목에 `P1`·`P2`·`P3`을 넣으세요. 이미 사람이 붙인 `priority:` 라벨은 존중합니다. 난이도는 사람이 `effort:S`, `effort:M`, `effort:L` 중 하나를 붙이면 됩니다.
6. 예전 이슈를 한 개씩 검토하려면 **Actions → Issue triage and fair assignment → Run workflow**에서 `issue_number`를 입력합니다. `dry_run=true`는 미리보기만 수행합니다. 결과를 확인한 다음 `dry_run=false`로 실행하면 됩니다. **고정 역할 이슈에는 이 기능도 쓰기하지 않습니다.**

자동 생성되는 영역·우선순위·난이도 추정 라벨은 실행 시 GitHub API로 생성합니다. `routing:hold`는 팀 관리자가 한 번 수동 생성해야 합니다. **기존에 사람이 정한 assignee는 자동 변경하지 않습니다.** 기능 인계(총괄→AI), 공식자료 별도 요청 이슈 생성·공동 assignee 추가, 인적 리뷰어 지정은 이 봇이 수행하지 않는 후속 단계입니다.

## 안전 범위 및 검증

- 워크플로는 기존 `issue-initial-routing.yml`을 확장합니다. 별도 초기 배정 워크플로와 중복 실행하지 않습니다.
- GitHub `GITHUB_TOKEN`의 `issues:write`와 `contents:read`만 사용하며, 외부 토큰·유료 API는 필요하지 않습니다. 이슈 제목·본문을 셸 명령으로 실행하지 않습니다.
- 보호 이슈·수동 배정은 유지하고, 애매한 문제는 검토 대상으로 보류합니다. 담당자 배정이 GitHub API에서 거절되면 `triage:needs-review`로 기록합니다.
- GitHub Actions의 동시 실행은 리포지터리 단위로 직렬화합니다. 완전한 일정·휴가·PR 리뷰 시간을 자동 인지하는 것은 아닙니다.
- 테스트: `node --test tests/automation/issue-router.test.cjs` (보호 이슈, 최초 배정, AI 공정 배정, 수동 배정 유지, 모호함, 수동 홀드, dry-run, 오류 복구).
- 코드나 문서 변경만으로 실제 운영 환경에서 GitHub Actions 실행이 성공했다고 주장하지 않습니다. PR HEAD의 CI와 기본 브랜치 활성화 결과를 따로 확인해야 합니다.
