### 기존 기능을 설명할 때 반드시 고칠 주장

1. "학교 밖 활동을 입력할 수 없다"는 **틀리다**. 이미 외부비교과 신청·증빙·승인 기능이 있다. 실제 교외 프로젝트/오픈소스 링크와 자유기술 스킬을 받는 필드인지, 추천으로 자동 이어지는지는 **로그인 후 확인 전**이다.
2. "진로목표/로드맵/포트폴리오가 없다"는 **틀리다**. 진로방향 지정·다중 목표, 학과전공 로드맵과 이력서/자소서 공개범위까지 있다.
3. "교외채용을 보여주지 않는다"도 **틀리다**. 일반·추천·지역별 채용, 외부 워크넷, 아르바이트·교외 채용행사, 대외활동이 있다. 우리 제품의 차별점은 **실제 지원자격 + 학생이 승인한 구체적인 기술/경험 + 두 전공(A/B) 컨텍스트를 함께 사용하는 설명 가능한 추천**이어야 한다.
4. "대시보드가 전혀 개인화되지 않는다"도 부정확하다. 2024 매뉴얼은 포틀릿 편집·이동을 설명한다. 개인에게 필요한 정보가 첫 화면에 어떻게 노출되는지는 **실제 사용성 테스트**로 검증할 문제다.
5. "모바일에서 사용할 수 없다"는 주장도 근거 부족. HUFS+에서 HUFSAbility 진입 경로가 공식 안내되어 있으며 비교과 키워드의 앱 푸시 기능도 소개돼 있다. 모바일 UX 불편은 페이지 전환 횟수·검색시간 같은 측정치로 제시한다.

### 원래 자료에서 관찰되는 세부 특성

- 진단 결과는 **연도별 조회**가 가능하다. 핵심역량 진단은 매년 시행된다. 그러나 모든 종류의 HUFSAbility 추천 프로필이 오직 연 1회만 갱신된다는 결론은 아니다.
- 외부비교과는 등록 즉시 자동으로 인증되는 것이 아니라 **관리자 검수/승인** 절차가 있다.
- 채용 추천신청은 사용자가 이력을 확인하고 취소할 수 있다.
- 이력서·자기소개서 등은 **공개 여부를 학생이 설정**할 수 있고, 공개 시 관리자가 확인 가능하다고 매뉴얼에 쓰여 있다.
- 상담/심리/대학생활 적응검사는 개인정보 보호 수준이 높으므로 제안 AI의 자동 데이터 수집 경로에서 제외한다.
- 학교 공식 역량인증 설명에 따르면 교과학점/성적 및 내부·외부 비교과 활동을 기준으로 역량점수가 환산된다. 이런 점수는 Linux·Git·오픈소스 협업처럼 개별 기술 스킬을 정확히 증명하는 것과 다르다.
- **비교과 키워드 구독**은 별도 공식 매뉴얼과 학교 뉴스레터에서 확인된다. PDF 원본은 내려받았지만 그 매뉴얼의 전체 UI 필드·처리 로직까지 직접 재검증하지는 못했다.

## 4. 우리 웹사이트에 필요한 구성 요소: 복제가 아닌 설계

현재 HUFSAbility의 화면 구조로 확인된 것은 공개 로그인/목록/상세/채용·활동이다. **웹사이트 목표는 독립 반응형 웹/PWA**다. 추후 학교 협의 시 공식 HUFS+에서 웹뷰·딥링크로 열거나 별도 HUFSAbility 보조 앱/PWA로 배포할 수 있다.

- **오늘:** 내 필수 학사 알림, 신청 가능한 공모전·대회·채용 Top 3, 비개인화 전체 발견 6, 출처·마감·지원상태.
- **내 경험:** 두 전공 A/B, 희망 진로, 학생이 선택해서 제공한 방학/교외 프로젝트, CLOVA가 제안하고 학생이 승인한 SkillTag.
- **기회 탐색:** 학교 비교과·장학·공모전·교외채용을 같은 기회 데이터 구조로 정규화해 검색/필터.
- **수강·졸업:** 공식 확정 분반 수강신청 시간표(P1), 검증된 두 전공의 소형 졸업 규칙(P1), 다음 학기 강좌 개설 전망(P2).
- **개인정보/오프라인:** 승인 태그·출처·동의/삭제 제어; 발표장 인터넷 없어도 합성 공고·학생 프로필로 자격·추천 계산. 오프라인 CLOVA 결과는 사전 결과 재생임을 명시.

**독립 UI에서 학교 HTML·CSS·학교 로고를 그대로 복제하거나 학교 포털처럼 보이는 가짜 로그인 페이지를 제작하지 않는다.** 기존 화면의 *정보 구조와 필드*만 참고한다. 공식 앱/학교 데이터 연동은 별도 학교 승인.

## 5. 11월 6일 회의 전 HUFSAbility 본인 계정으로 확인할 것

1. 실제 모바일/PC에서 첫 화면부터 지원 가능한 비교과 1개를 찾을 때 필요한 클릭·시간.
2. 학생 포틀릿 편집으로 채용/비교과를 첫 화면에 표시할 수 있는지.
3. 외부비교과의 자유 서술·실적 링크·증빙 업로드·승인 필드; 오픈소스 프로젝트도 등록 유형이 있는지.
4. 키워드 구독의 단어 선택 범위, 사용자 직접 추가 여부, 푸시가 실제로 작동하는지.
5. '추천채용'의 추천 이유/학년·학적·진로 기반 필터가 사용자 화면에서 설명되는지.
6. **이중전공 A/B**와 기존 이수내역이 어느 정도 노출되는지, 정식 PDF/CSV 내보내기 기능이 있는지.
7. 학교 비교과·외부채용·장학/공지의 목록 전환·검색/정렬과 전체 접근성.
8. 공식 앱 HUFS+에서 HUFSAbility 접근 시 불편한 실제 단계. 학생 계정이나 개인정보를 캡처해 공유하지 않는다.

**이 미확인 항목들은 '존재하지 않는 기능'으로 보고하지 않는다.**

## 6. 다른 AI와 GitHub 협업 권장

- 팀 개발에 **Private GitHub 저장소 권장**. 현재 CodexPro의 Git 상태 조회에서는 naver_competition이 아직 Git 저장소로 인식되지 않았다. .gitignore만 있다고 GitHub 연결이 된 것은 아니다.
- 초기 커밋은 작성한 제품 문서/기능 조사 Markdown, feature_catalog.json, 출처 목록 및 해시만. 원본 HTML/CSS/PDF/스크린샷/실제 공고 본문과 학생정보는 GitHub에 올리지 않는 것이 안전하다(재배포 허가 여부 미확인).
- 팀원은 Issues로 역할과 출처 확인 요청을 나누고, main 보호 + 기능별 브랜치 + PR 검토 후 병합. 개발은 11/6 합의 후 시작.
- 기존 retire/ 전체와 .env, NCP API 키, 종합정보 로그인/성적/개인 동의 문서는 절대 커밋하지 않는다.
- 팀원이 소스 데이터를 재현할 필요가 있으면 공식 URL·정규화 스키마·데모용 합성 fixture를 공유하고, 공개 데이터 원본 자체 공유는 학교 이용허락 확인 후.

### 8.2 공식 사이트에서 직접 보인 추천 실패 위험의 구체 사례

**사례 A: 이번 2026 AI 캠퍼스 공모전.**
- 구조화된 핵심역량 비중: 창의혁신·대인관계·세계시민·의사소통 각각 25%; 지식·정보·기술 활용역량 **0% 배정**(선언된 6대 역량 중). **0점이 대회에 기술적 역량이 없다는 뜻은 절대 아니며, 해당 공고의 교육역량 메타데이터일 뿐**.

### 8.3 Naver Cloud 활용: 이 경우가 '필요한 이유'

1. **P0 CLOVA Studio HCX-007 Structured Outputs**: 프로그램 자유문장에서 *추가 자격요건·실제 신청 URL·팀장/팀원별 행동·필요 서류·지원마감 vs 행사기간·근거 문장*을 JSON 후보로 생성. 원본 정형 필드를 넘겨쓰지 않고 규칙 엔진 교차검증. [N1]
2. **P0 CLOVA Studio HCX-DASH-002/007**: 학생 자발적 프로젝트 텍스트에서 Linux/Python/Git/운영·금융융합 등의 구체 SkillTag 후보와 관심 진로를 추출; 학생 승인 후만 검색. [N2]
3. **P0 NCP Server(VPC) + Object Storage**: PWA 공개 실행, 출처/원문 해시·승인받은 공고 스냅샷 저장, 오류 로그·모델 사용량 실증. 학생 실명 성적·민감상담 등은 동의/계약 없이 NCP 전송 금지.
4. **P1 Cloud Search**: 한국어 형태소·동의어/불용어와 다국어 검색, 예: '리눅스 운영'→'시스템 관리·인프라' 후보 연결. **유료 컨테이너/색인/요청 과금이 있으므로 소량 MVP에는 정규화 SQL/로컬 검색 우선**, 데이터 규모가 늘고 검색 품질 비교가 확보될 때만 채택 [N3].
5. **P2 CLOVA OCR**: **이미지형** 외부 자격증/수료증만, 학생이 선택·동의해 제출한 경우에 한해 텍스트 추출. 공개 HTML의 이미 정형화된 필드에 OCR을 쓰지 않는다. 서비스 플랜에 따라 기본 유지비 존재, 본선 필수 기능 아님 [N4].
6. **P2 Papago Translation**: 외국인 학생을 위한 공지·기회 안내, 공식 원문·학사 기준 우선/번역 근거 동시표시. 일부 API는 브랜드 표기 조건 등 확인 필요. 한국외대×NCP의 **2026.03.16 AI 스마트캠퍼스·다국어 행정 협력 발표**와 장기 방향 부합. 본선 P0에서 모두 구현하지 않는다 [N5][S13].
7. **학교의 정보 공급이 학생의 수요를 뒤따르는가? (운영 관점의 추가 가설)**: 기존 HUFSAbility에는 만족도·설문·역량검사가 이미 있다. 그러나 **학생이 하고 싶은 방학 프로젝트/부족한 교육 기회를 자발적으로 입력 → 익명·집계한 수요를 학과/교육혁신원에 전달 → 새로운 비교과·산학 프로그램 기획 → 실제 지원·성과 확인**으로 이어지는 피드백 루프가 어느 정도 자동화되는지는 확인되지 않았다. NCP/CLOVA로 동의한 문장의 주제를 분류하고 **집계 가능한 충분한 표본인 경우에만** 비식별 대시보드 제안(P2). 원문/소수집단/개인 연락처를 학교에 자동 공개하지 않는다. 2026.03.16 양 기관 협력 발표는 Naver Works 스마트 행정도 추진계획으로 언급하지만 현재 제휴 API/연동 승인은 없다 [S13].
8. **AI가 하면 안 되는 일**: 졸업/학점 인정·자격·마감의 최종 판정, 교수 퇴임 날짜 추측, 학교 공식 승인이나 학생 프로젝트 실적 인증. 이들은 결정론 규칙+공식 원문/관리자 확인.

### 8.4 3주 본선에서의 범위와 실험 계약

**시연 필수 수직 흐름(P0):**
- 합성 **이중전공 A/B 학생 프로필** → 학생이 프로젝트/방학 경험 한 문장 입력 → CLOVA SkillTag 제안→ 학생 승인 → 학교 공개 비교과·교외채용·공모전 20~30건 중 적격/마감과 본문 추가조건 검사 → 추천 3/일반 탐색 6 + 원문 근거 → **팀장·팀원별 신청 체크리스트 사례** → NCP Server/CLOVA 실제 호출 로그.
- 인터넷 불가 발표: 같은 웹 UI·결정론 코어를 localhost로 작동, 사전 기록된 CLOVA 결과는 **replay**라고 표시한다.

**측정:** ① 태그 추출 정확도/학생 승인 전후 차이 ② 추가 자격 및 접수 경로 발견 재현율 ③ ELIGIBLE 오판율/UNKNOWN 비율 ④ 신청과제 완료 단계/정보발견 시간·클릭 ⑤ 3:6·필수공지/전체보기 접근성 ⑥ NCP 실제 입출력 토큰·비용 및 장애 폴백.

**P1 이후:** 두 전공의 검증된 졸업규칙 일부·확정 분반 시간표(코드), 다음 학기 개설 전망·교원 공식공고(P2)는 데이터 확보/백테스트 이후에만.

**현행 시스템 비판을 검증하는 5명 인터뷰:** 개인화 피드가 없다는 문구로 질문을 유도하지 말 것. 같은 과제에서 HUFSAbility로 실제 몇 단계가 필요한지/신청 조건을 올바르게 찾는지/외부비교과의 프로젝트 자유서술·키워드 구독이 얼마나 유연한지 중립적으로 측정한다.
